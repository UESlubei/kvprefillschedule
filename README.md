# kvprefillschedule

根据请求能复用的 GPU/CPU KV 缓存调整 vLLM 等待队列顺序，并测量它对输入计算量、首 Token 延迟和吞吐的影响。

本仓库包含项目完整源码、测试、补丁、实验脚本、依赖版本、参考成本表和实现报告。模型权重、Python/CUDA 环境、离线环境包、逐请求结果、日志和性能分析文件不在仓库中。

- [实现报告：代码如何工作、遇到的问题及解决办法](docs/IMPLEMENTATION.md)
- [环境和运行说明](docs/RUNNING.md)
- [源文件校验清单](SOURCE_MANIFEST.json)

## 修改了什么

1. GPU 策略：每轮查看等待队列前 8 个请求，只读查询可复用的 GPU 前缀长度，优先执行命中较长前缀的请求。
2. GPU/CPU 策略：继续查找 CPU 上连续 Ready 的 KV，结合实测 Prefill 和 CPU→GPU 搬运时间估算可节省的时间，再排序。
3. 排序只作用于尚未执行的普通等待请求；已执行、抢占恢复和异步输出状态形成边界。等待超时的请求优先处理。
4. 旧版另外实现了重算/恢复成本相关的抢占策略，保留其负向实验结果。新版 0.32.0 只移植请求排序，保留原生抢占。

原生 vLLM 继续负责前缀缓存、KV 分配、CPU Offload、LRU、数据搬运和模型执行。当前代码不对每个 KV Block 预测未来价值，也不改变新版缓存淘汰规则。

## 已测结果

RTX 3090 24 GiB，Qwen3-1.7B FP16；主动限制 KV 预算。相对未修改源码的官方 vLLM 0.32.0，默认 Async/CUDA Graph 路径中：

| 策略 / 场景 | P95 首 Token 延迟变化 | 固定负载输出吞吐变化 | 冷请求平均首 Token 延迟变化 |
| --- | ---: | ---: | ---: |
| GPU 排序 / 共享前缀，640 Blocks | -11.34% | +0.41% | +14.85% |
| GPU/CPU 排序 / 混合缓存，1024 Blocks | -13.36% | +0.15% | +21.85% |

主结果各有 5 对种子，每 Run 256 请求。55 个同步正式 Run、40 个默认路径正式 Run 已完成。C 的吞吐变化区间跨零；固定输入速率也不能用来证明最大服务容量。同步 Eager 下测得的较大收益与默认路径结果分开记录，见实现报告。

正确性专用对照、取消恢复和缓存路径检查提供有限证据。压力运行有逐 Token 分歧，原严格概率检查未全部通过；不将其描述为所有输出完全一致。
